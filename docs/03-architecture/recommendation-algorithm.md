# 하루 일정 계산

> 구현 위치: `apps/api/src/domain/` — `plan-day.ts`(일정), `travel.ts`(이동), `opening.ts`(영업시간), `spot-summary.ts`. 모두 **순수 함수**(입출력만, I/O 없음)
> 설계: [`../01-product/day-course-design.md`](../01-product/day-course-design.md) 6장 (2026-11-01 조정 반영) · 결정: [ADR 0005](../00-overview/decisions/0005-day-plan-coordinates-hours.md)

```ts
function planDay(spots: Spot[], query: DayQuery): DayPlan
```

## 원칙

1. **결정적**: 같은 입력이면 항상 같은 출력 (URL 공유 보장). 난수 · 현재 시각(`Date.now`) 사용 금지. 요일은 `date` 문자열의 달력 날짜로 계산한다. 입력 배열 순서가 달라도 결과가 같다 (동률은 항상 id로 정리).
2. **문 연 곳만**: 모든 항목은 그 요일 영업 구간 안에서 도착 · 체류를 마친다. 마지막 항목의 `leaveAt` ≤ `end`.
3. **설명 가능**: 관광 항목마다 `matchedTags` · `score`, 빠진 관광지마다 이유, 넣지 못한 블록은 `notices`로 남긴다.

## 상수

| 상수 | 값 | 쓰임 |
|---|---|---|
| `TRAVEL` | 도로 보정 1.4, 평균 40km/h, 주차 · 걷기 5분, 5분 단위 올림 | 이동 시간 |
| `MEAL_WINDOWS` | 점심 11:30–13:30, 저녁 17:30–19:00 | 식당 **도착** 창 |
| `MEAL_MINUTES` | 60 | 식사 시간 (식당의 `stayMinutes`와 무관) |
| `DAY_LIMITS` | 점심 조건 `start ≤ 12:00 && end ≥ 14:00`, 저녁 조건 `end ≥ 18:30` | 넣을 식사 정하기 |
| `START_CANDIDATES` | 5 | 시작 장소 후보 수 |
| `TRAVEL_WEIGHT` | 0.5 | 관광 가치의 이동 · 기다림 감점 |
| 점수 (plan-day.ts 안) | 일치 태그 1개당 10, 동행 일치 5 | 후보 점수 |

## 이동 시간 (`travel.ts`)

```
거리(km) = haversineKm(a, b)                         // 지구 반지름 6371km
이동(분) = 0                                          // 거리 0일 때
        = ceil5( 거리 × 1.4 × 60 ÷ 40 + 5 )            // 그 외
```

- 예: 5.56km → 16.7분 → **20분**, 0.11km → 5.2분 → **10분**.
- 첫 항목은 출발지가 없으므로 이동 0 · 거리 0. 응답의 `distanceKm`는 소수 1자리로 반올림한다.

## 영업 맞추기 (`opening.ts`)

```ts
fitVisit(spot, weekday, arriveMinute, stayMinutes): { arriveMinute; waitMinutes } | null
```

그 요일 영업 구간을 이른 순서로 보며, `실제 도착 = max(도착, open)`이 `실제 도착 + 체류 ≤ close`이고 `실제 도착 ≤ close − lastEntryBeforeCloseMinutes`인 첫 구간을 고른다. `waitMinutes = 실제 도착 − 도착`. 맞는 구간이 없으면(휴무, 마감 임박, 입장 마감 지남) `null`. 쉬는 시간 사이에 도착하면 다음 구간 시작까지 기다린다.

## 단계

### 0) 기다림 허용

도착이 영업 시작이나 식사 창 시작보다 이르면 그때까지 기다린다. `arriveAt`은 기다린 뒤 시각이고, 기다린 시간은 `waitMinutes`로 담는다 (`slackMinutes`에 포함). 첫 장소도 같다 — 08:00 출발, 09:00 개장이면 09:00 도착 · 기다림 60분.

### 1) 후보 · 점수

- `kind=spot`만, `exclude`에 있는 곳은 뺀다.
- 점수 = 일치 태그 수 × **10** + 동행 일치 **5**. 0점은 뺀다.
- 일치 태그가 1개 이상이면 **1순위 후보**, 동행만 맞으면(5점) **보충 후보**.
- 후보 정렬: 점수↓ → id↑.
- `food` 관심사는 관광지 점수에만 쓰고 식당 · 카페 선택에는 쓰지 않는다.

### 2) 시작 장소 후보

1순위 후보 중 **그 요일에 여는** 곳 상위 5곳 (1순위가 하나도 없으면 보충 후보에서). 시작 장소마다 3~5단계를 끝까지 돌려 일정을 최대 5개 만든다. 첫 관광은 시작 장소를 먼저 시도하고, 그 장소가 3단계 조건에 맞지 않으면 일반 선택을 한다. 후보가 없으면 시작 장소 없이 한 번 돈다.

### 3) 관광 선택 (탐욕)

현재 위치 · 시각에서, 아직 안 간 후보 중 아래를 모두 만족하는 곳을 고른다.

- `fitVisit`이 통과하고, 체류를 마친 시각 ≤ `end`
- 남은 식사가 있으면: 체류를 마친 시각 + 가장 가까운(아직 안 간, 그 끼니 · 그 요일 영업) 식당까지 이동분 ≤ **식사 기한** = min(식사 창 마감, `end` − 60분)
- 저녁이 남아 있으면: 그 요일에 19:00 넘어서까지 여는 관광지(야간 관광 후보)는 **저녁 뒤로 미룬다**

1순위 후보 중 맞는 곳이 있으면 그중에서, 없을 때만 보충 후보에서 고른다. 고르는 기준은 **가치 = 점수 − 0.5 × (이동분 + 기다림분)**↓ → 이동분↑ → id↑.

### 4) 식사 · 쉬어 가기

- 넣을 식사: 점심(`start ≤ 12:00` 이고 `end ≥ 14:00`), 저녁(`end ≥ 18:30`).
- 시각이 식사 창 시작 이상이 되었거나, 3단계에서 고를 관광이 없으면(기한 안에 다녀올 곳이 없으면) 식사를 넣는다.
- 식당: 그 끼니(`meals`)에 맞고 그 요일 영업하며 **그날 아직 안 간** 곳 중, `max(이동 후 도착, 창 시작)`에서 `fitVisit`(60분)이 통과하고 도착 ≤ 창 마감, 식사를 마친 시각 ≤ `end`인 곳. 이동분↑ → id↑.
- 점심 뒤에는 **쉬어 가기**: 안 간 카페 중 `fitVisit`(카페 `stayMinutes`)이 통과하고 끝 시각 안에 마치는 곳. 식당에서 이동분↑ → id↑. 저녁 뒤에는 쉬어 가기를 넣지 않는다.
- 넣을 곳이 없으면 그 블록을 건너뛰고 `notices`에 남긴다: `이 시간에 영업하는 식당을 찾지 못했어요` / `이 시간에 영업하는 카페를 찾지 못했어요` (같은 문장은 한 번만). 그 요일 그 끼니에 여는 식당이 아예 없으면 바로 식사를 건너뛰고 같은 안내를 남긴다.

### 5) 끝

저녁 뒤에도 3단계를 계속 돈다 (야간 관광). 더 넣을 관광도 남은 식사도 없으면 멈춘다.

### 6) 일정 고르기 · 결과 구성

- 5개 일정 중: 관광 점수 합↓ → 총 이동분↑ → 시작 장소 id↑.
- `excluded`: 1단계 후보(보충 후보 포함) 중 고른 일정에 관광으로 없는 곳, 후보 순서대로. 그 요일 영업 구간이 없으면 `CLOSED_ON_DAY`, 그 외 `NOT_ENOUGH_TIME`. `exclude`로 뺀 곳과 0점인 곳은 없다.
- `totals`: [`data-model.md`](data-model.md#하루-일정) 참고. 관광이 0곳이어도 200으로 돌려준다 (화면은 빈 결과 상태).

## 검증 기록

- **기준 구현 차등 비교**: 설계 6장 규칙을 따로 짠 기준 구현(커밋하지 않음)과 실제 `spots.json`에서 무작위 쿼리 2,000개(날짜 · 시각 · 동행 · 관심사 · exclude)의 응답 JSON이 2,000개 모두 같았다 (프롬프트 12 · 13).
- **실제 데이터 전수 점검**: 7일 × 시작 7 × 끝 5 × 동행 4 × 관심사 31 = 30,380 쿼리에서 관광 0곳 일정 0, 점심 · 쉬어 가기 누락 0, 저녁 누락 0. 21:00까지 일정의 89%가 저녁 뒤 야간 관광을 포함했다. 60분 넘는 기다림은 08:00 출발의 첫 장소(개장 대기)뿐이었다 (프롬프트 16).
- 기록: [`../05-copilot/review-log.md`](../05-copilot/review-log.md)

## 알려진 한계

- 이동 시간은 직선거리 어림값이다. 실제 도로 · 교통과 다를 수 있다 (화면에 안내 문구).
- 공휴일 · 명절 · 달마다 다른 휴무는 계산하지 않는다 (`hours.note`로만 안내).
- 탐욕 방식이라 최적해(가장 많이 담기)를 보장하지 않는다. 시작 장소 5개로 결과 품질을 보완한다.
- 식사 기한 판단에 쓰는 "가장 가까운 식당"은 그 시각 영업 여부까지는 보지 않는다. 실제 식당 선택(4단계)에서 영업을 다시 확인하고, 못 찾으면 `notices`로 남긴다.
